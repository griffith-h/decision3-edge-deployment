## 3. 每轮循环

**跑测试 → 发现慢请求或失败 → 保存证据并停止本轮扫描 → 定向 profile → 改一个主要瓶颈 → 回归与复测 → 接受或撤回 → 继续发现下一个问题。**

第一轮使用已暴露的 7,232-token 单问题、两条约 4,600-token 多问题和 32 问题超时请求，补充短输入与 615-token 保护用例。冻结请求 ID、载荷哈希、题组、已有输出及引擎身份；开发用例是原样本的固定视图，不修改原 1,000 条。

先保存实际每批 B/T、有效 token、padding、耗时、回退计数增量和峰值内存。多问题的 `usage.input_tokens` 是合计值，不等于单条序列长度；预热累计计数不能当作当前请求命中。

### B. 尽早停下来诊断

| 现象 | 开发轮的动作 |
| --- | --- |
| 新发现、未登记的请求超过 30 秒 | 标记慢请求，收集组件耗时及进度，不再继续扩大本轮扫描 |
| 已登记的慢请求未达到自己的阶段目标 | 按其 60/30/120 秒目标继续定向优化；已经达标的已知用例不因超过通用 30 秒阈值而反复阻断扫描 |
| 达到 120 秒仍未完成 | 开发诊断到此为止，安全终止专用实验进程并清理；记录“开发预算内未完成”，不伪称正式 600 秒超时 |
| OOM、崩溃、非有限输出、输出字段缺失 | 立即进入故障定位；记录最后完成阶段和资源情况，停止性能比较 |
| 主要耗时集中在回退或初始化 | 定位具体保护条件、分配/编译/缓存生命周期；合法且不慢的回退无需强行消除 |
| 只有一条孤立慢记录 | 先确认输入形状、首次准备和复现情况，不直接写复杂新实现 |

**正确性参照例外：** 仅r018的CPU参照按模型原批次边界分成8/8/2三个调用，每批最多600秒，以保持原B/T、顺序、padding和完整问题。额外prepare与分次传输不计为性能对照，也不改变原1,000条正式协议。每批必须核验所有NPU及图调用增量为0；完整18问题和生命周期检查通过后才可成为此题组的原CPU参照。开发候选仍按120秒预算，原逐行参照和负面证据保留。

**一次完整题组核验：** 两问题诊断已恢复数值一致后，仍需知道完整18问题的实际输出。允许对冻结的同一完整题组做一次独立完整性核验，使用原正式600秒上限，不改变输入、原批次、模型或评分门槛；目的为核对原8/8/2 CPU参照与原生题组指标。它不属于120秒开发初筛达标，也不把超过120秒写成速度目标通过。运行前记录用途、候选身份和参照；超过600秒保留失败。之后按实际全题组结果选择下一轮，不反复仅测两问题或无限延长预算。

诊断按阶段持续落盘，允许获得不完整 profile。完整性能计时须在无 profiling 包装下重测；不以 profiling 日志代替正式成绩。正式验收仍使用原 **600 秒**请求上限，两个协议明确分开。

每轮板端诊断与初筛先控制在 **45 分钟运行预算**内；到预算就整理证据、选择下一步，不再无期限等一条请求。候选已经明显无效时提前结束。正式验收不套用该开发轮预算。

### C. 一次解决一个主要瓶颈

先测占比，再决定实施顺序。目前的候选方向是：

1. **长投影和 MLP**：确认超过原行数保护后的实际 CPU 成本，研究有内存上限的分段执行与完整输出合并。
2. **长注意力和扫描**：确认超过 2,048 长度后的耗时与内存，保留完整注意力、mask 和扫描状态语义。
3. **多问题调度**：确认实际批次及 padding 放大；验证按长度组织批次或调整批量的收益，恢复原问题顺序与独立性。

这不是预设根因。首轮已确认 32 问题存在 padding 放大和 2,048 行保护后的 CPU 线性回退；单条 7,232-token 另有长线性、注意力和扫描成本。后续不直接放开 native guard，不同时叠加多个未经验证的改动。

**r044之后的候选顺序：** 先取得完整18问题的原批次数值及原生题组指标；未通过时继续定位精度，暂缓性能改写。通过后，优先审查重复的中间输出搬运：当前MLP/投影先执行带保护的BF16输出，再读取同一FP32 C用于修复，前一份结果被丢弃。若改为单次FP32私有读取，必须保留原`abs(raw)>=65488`、非有限、输入范围、全部worker先join、整层/整组CPU重算、句柄归原Owner及115/615旁路；先实际SDK布局/边界与故障顺序检查，再重复同一请求。这是待验证方案，不能记为已经提速。

### D. 小范围复测，决定是否保留

- 先跑最接近改动的正确性与失败路径检查，复测触发问题的完整请求。有既有测试覆盖时复用，不默认扩建测试体系。
- 初筛每条完整调用 1 次，只用于发现问题。通过后对慢请求做少量同环境配对复测，对短输入和 615-token 做 5 组配对；不能用 1～3 次数据宣称可靠 P95。
- 初始保留标准：目标慢请求中位数改善至少 **20%**，或原预算内未完成的请求首次完整成功；同时数值门槛通过、已有快路径退化不超过 10%，其他已知用例无新错误。小幅收益仅在消除明确稳定性/内存问题时另行说明保留理由。
- 旧版本身超过开发预算时，速度只报告带下界的比较；不捏造精确倍数。历史 320.41 秒可作初筛参照，不能冒充本轮同环境配对结果。
- 准备保留候选时跑既有 34 例回归、已积累的慢请求，以及实际触及的长度切换、故障回退、资源释放检查。原 probability / score / noul 的 0.01 门槛不放宽，choice 保持；confidence 独立披露。
- 无收益、错误或未解释回归的候选撤回；保留负面记录，以最后合格版本作为下一轮起点。
- 组件已有收益、整条请求仍超过开发预算时，可保留为未完成实验继续改进；不能替换最后合格版本，也不能把局部加速冒充整条请求已加速。

### E. 扩展覆盖，再进入下一轮

已知用例改善后，先覆盖 43 个基准各至少一个完整题组，并兼顾输入长度、问题数；事先根据元数据固定清单，预计约几十至百余条，以实际完整题组数为准，不硬截为 50/100 条。然后向原 1,000 条中尚未检查的请求扩展；再次遇到慢请求或故障，就回到 B。

这是**发现问题的开发扫描**：每个版本独立记结果，保留检查进度，避免每次优化都先重复扫过同一批快请求。跨版本扫描记录只用于问题覆盖，不能拼成一个版本的完整速度或准确率成绩。已经用于调优的用例须明确标为开发用例。

## 5. 什么时候完整验收并部署

当已知慢请求达到阶段目标、保护用例通过，且开发扫描未再暴露阻断问题时：

1. **冻结一个候选版本**，从头完整跑原 1,000 条、原顺序、原 600 秒上限；加载、预热与首次形状成本按既有协议记录。
2. 正式轮若暴露新的主要问题，保留本轮结果，转回优化。改动引擎后另起正式目录，从头验收；不在同一轮中热替换算法再拼接结果。
3. 报告完成率、错误/超时/OOM、总耗时、板端与通信 P50/P95、按长度和问题数分组的结果，以及原评分器的各任务指标。
4. 只有存在完整可比参照时才宣称完整集“准确率不降”。现有 7 条输出和 34 例数值回归不能证明这一点；旧版超时用例也不能声称与不存在的完整输出一致。本轮可以如实报告最终版本绝对得分和已有可比集合的差异。
5. 达到目标并完成结果评审后，在 8901 做 34 例输出回归、接口、不同请求并发隔离、长度切换和恢复检查，再切换 8900 并复验，保留回滚。沿用 [部署流程](README.md#全部完成后的部署)，不因开发用例变快就直接发布。
