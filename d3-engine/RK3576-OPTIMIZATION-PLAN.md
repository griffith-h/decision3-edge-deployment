## 第一优先级是长注意力

发票第一轮的 1,225.57 秒里，ARM 上的 FP32 注意力占 **644.85 秒（52.6%）**，RKNN 矩阵乘连同打包、搬运与同步占 **259.75 秒（21.2%）**。后者也包含 CPU 和等待时间。假设其余时间固定且没有额外搬运，把注意力加速 2 倍，整单估算为 **903 秒，约 15 分 03 秒**。即使将这 644.85 秒全部省掉，仍有约 581 秒。因此先验证注意力，再用同一张发票查第二个瓶颈。[发票逐轮算子计时](results/workflow-npu.json)

1. **让 NPU 分块计算长注意力的两次矩阵乘。** 先分别覆盖状态读状态的方阵，以及一组问题读「公共状态和本题」的长方阵。现有 edge 实验快路径限于不超过 8,192 的方阵，无法直接覆盖这张发票。候选从每块 64/128 个查询、256/512 个键开始，测 `QKᵀ` 和概率权重乘 `V` 的 FP16 输入、FP32 累加。ARM 先负责掩码与在线 softmax，以 FP32 为每个查询跨全部有效键维护最大值、分母和加权和。覆盖不同问题长度、组内填充、全屏蔽行和不足一块的尾部，以检查点输出校验舍入和屏蔽语义。小矩阵、超出数值范围和不支持的形状沿用现有路径。[Rockchip MatMul API 示例](https://github.com/airockchip/rknn-toolkit2/blob/master/rknpu2/examples/rknn_matmul_api_demo/README.md) · [分块注意力算法](https://arxiv.org/abs/2205.14135)
2. **按请求复用 K/V 和缓冲区。** 在 nano 的同一请求、同一层内，让各问题组直接读取同一份状态 K/V，保留各自的问题 K/V 和掩码。按块转换精度和布局，记录读写字节、转换次数和等待时间。以单个头为例，8,902² 个 FP32 分数需要约 302 MiB，128×512 的分数块只需 256 KiB。这是临时分数的大小估算，实际节省以整单峰值为准。异步提交时，上一块的设备操作完成后才可复用缓冲区。跨请求隔离状态，edge 继续使用自己的整行注意力。[当前状态与问题分组实现](engine.py)

## 各硬件怎样分工

R76S 16 GB 版配有 LPDDR5。RK3576 集成 4 个 Cortex-A72、4 个 Cortex-A53、Mali-G52 MC3 和双核 RKNPU，共用 32 位内存接口。片上张量运算交给这颗 NPU，厂商框图未列独立 TPU。标称 6 TOPS 对应稀疏 INT8 峰值，本方案以真实形状的端到端耗时选择路径。[Rockchip 芯片框图与规格](https://www.rock-chips.com/uploads/pdf/2024.3.18/192/RK3576%20Brief%20Datasheet.pdf) · [FriendlyELEC R76S 板卡规格](https://www.friendlyelec.com/index.php?product_id=308&route=product/product) · [板端记录](results/board.json)

| 资源 | 下一轮候选 | 如何决定去留 |
| --- | --- | --- |
| A72 / A53 | A72 运行 FP32 归一化、递推和 NEON 内核。比较 3 与 4 个大核线程，限制 OpenMP、BLAS 和 PyTorch 总并行度。A53 先试分词、JSON 和准备下一块输入 | 分开记录各阶段、线程迁移和温度。把分词迁到小核后，短请求也要重新计时 |
| 双核 RKNPU | 保留投影和 MLP，先让独立的 gate/up 投影共享一次输入打包。对照单核、双核独立投影和双缓冲，再试长注意力块 | 把打包、拷贝、设备执行和同步分别计时。只有形状复用且等待能够重叠时才保留流水线 |
| Mali-G52 MC3 | 为长状态尝试单次提交尽可能完整的注意力计算。将 Q/K/V 送入后，在 GPU 内完成分块矩阵乘、掩码、softmax 和加权求和，最后返回输出。以 ARM 及 RKNN 候选作同形状对照 | 旧 edge 在 115-token 输入上，保留 CPU 注意力的候选为 331.88 ms，GPU 注意力为 537.00 ms。nano 需另测不同长度，计入转换、传输与同步，再决定分流阈值。[旧 GPU 整模型实测](../cpu-tail-experiment/logs/gpu-screen.json) · [隔离环境的 Mali 运行时](../cpu-tail-experiment/logs/gpu-private-runtime.json) |
| LPDDR5 与共享缓冲区 | 按同组最长题长限制填充，优先复用同一份输入布局、权重和临时区。先保持 8 GiB 容器限制、零交换，比较单缓冲和双缓冲 | 合同只复制卷积所需的最后 3 个 token 已少持有 408 MiB。家电分组上限从 4 放到 64 后反而由 52.63 秒升至 70.90 秒，RSS 从 6.51 升至 7.19 GiB。跟踪 RSS/PSS、cgroup 峰值、DMA 缓冲与可用的内存带宽计数，分口径报告。[合同缓存记录](results/rknn-fp32.json) · [家电分组对照](results/home-ablations.json) |

GPU 和 NPU 共用内存带宽。先单独测两条路径，再对彼此独立的计算测重叠收益。短请求若继续受提交成本主导，就保留已有 ARM + NPU 路径。冷启动另测权重预打包和常驻实例，缓存按权重版本、SDK 和布局区分。若计数显示后续瓶颈是权重读取，可用独立校准数据试投影和 MLP 的 INT8，保留 FP32 决策头，逐层对照现有路径，再回到整单验收。

## 验收顺序

1. **先看正确性。** 固定上述 13 条官方来源请求、检查点、题序和决策头。以 12 条已有 CPU 对照为准，精度优先模式需保持 58 个字段判断、每个选项概率差 ≤1 个百分点、Score 期望分差 ≤0.01。默认模式单列家电的已知偏差，逐项比较。发票先与已归档的 55 个输出和三套策略动作做回归，补齐整单 CPU 对照后再评估与 CPU 的概率差。两种模式都另报对官方共识的字段和动作命中数。
2. **再看整单净收益。** 用同一隔离容器和频率策略，单请求交替跑基线与候选，记录冷启动、输入形状、每轮热延迟、温度、峰值内存和交换量。第一阶段建议以发票热态中位数 ≤16 分钟为目标，长单各跑 3–5 次，列出每次耗时。对短路由做足重复再报 P50/P95，建议 P95 回退控制在 5% 内。达到目标后再测并发 1 和 2 的排队延迟、吞吐和峰值。
3. **RKLLM 单独验证模型语义。** 有相应接口时，先验证文本自注意力掩码、线性递推状态及 FP32 决策头，再与同一组 CPU 概率比较。已有 RKLLM 1.3.1 对 edge 的四题只对齐两题，最大概率差 75.27 个百分点。对 nano 的下一轮投入优先给支持这些语义的 RKNN 路径。[RKLLM 适配与原始对照](../rkllm-experiment/experiment-result.json) · [所需接口](../rkllm-d3-support/native-integration-requirements.json)
