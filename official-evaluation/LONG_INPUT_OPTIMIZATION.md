2026-10-19：用户要求暂停整批评测，利用已出现的长输入/多问题超时开展下一轮优化。下面是已有证据和待验证方案，不是新优化已实现或已加速的声明。

后续目标、循环步骤、诊断预算和验收条件统一以[执行计划](PLAN.md)为准。本文件保留瓶颈证据与源码依据；60/30/120 秒是计划中的待验证阶段目标。

## 源码已确认的适用边界

- `row-projection-experiment/row_projection.py`：默认 `max_rows=2048`，按展平后的 `batch × sequence` 行数判定。超出范围走原路径；不能简单把逐段 512 行运算的上限与整个输出/中间张量的内存成本混为一谈。
- `long-sequence-experiment/long_kernels.py`：注意力与扫描的扩展限定 `512 < T <= 2048`，另有批量、头数、类型、mask 等保护。长请求已有 guard 回退增量；仍需逐段计时判断各部分的耗时占比。
- `bf16-pipeline-experiment/native_owner.py`、`core_owner.py`：最新 native MLP/动态 NPU 注意力只接受特定 B1/T615 形状。它们不能代表任意长度已加速。
- 真实运行的模型默认 `batch_size=8`、`max_length=None`。32 问题超时需要记录各批实际形状与 padding，不能仅凭问题数认定为批处理根因。

## 下一步顺序

1. 将已观察到的 7,232-token 单问题、两问题慢请求和 32 问题超时请求作为**定向性能开发用例**，先保存精确 ID、载荷哈希与当前输出，保持原冻结 1,000 条样本不变。它们不再被描述为未接触的性能留出集。
2. 先记录每批实际 B/T、padding、分层耗时、投影/MLP/注意力/扫描占比、回退原因及峰值内存。单次诊断设置明确预算并逐段落盘；提前中断的 profile 只能标为不完整，不能作为官方得分或完整延迟。
3. 根据实测占比依次验证：可控内存的长投影与 MLP 分段、超过 2,048 的完整注意力/扫描路径、减少多问题 padding 的批处理计划。只有确认瓶颈后才实现对应扩展；不直接取消保护，不缓存答案，不截断输入，不减少问题或模型层数。
4. 每个候选先跑这些定向用例，再补短输入、615-token 既有快路径、长度切换、故障回退与资源释放回归。改善后再恢复整批评测；新引擎必须用独立结果目录，不混用暂停前旧版本输出。

## 验收边界

- 固定相同模型 revision、权重、12 层和非因果完整注意力语义；完整保留所有问题与选项。
- 先建立有证据的组件耗时分布，再确定速度目标；不在尚未测量时承诺长输入 2 秒或 32 问题小于某个时长。
- 保留既有 34 例数值门槛，confidence 单列；官方题目使用原评分器。有完整旧输出的慢请求逐项核对，旧版超时用例不能凭空声称输出一致。
- 短输入与既有 615-token 路径不得出现未解释回归；CPU4–7、8GiB、线程配置和镜像留档，峰值内存、首次形状成本与稳态性能分别说明。
- profiling 包装不得通过注册模块 forward hooks 或改变保护判断来意外禁用/启用加速；计时运行与无包装结果核验分开。重用现有 profiling 的范围计时方法，按实际新路径补充，而非套用 615-token 组件占比。
- 保持原服务可恢复，不将未经验证的新候选部署；定时任务继续停用。
