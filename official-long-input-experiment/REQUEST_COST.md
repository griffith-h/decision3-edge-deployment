# 约31秒请求的完整耗时账本

2026-10-20，RK3576，r087诊断；模型与r080数值合格计算路径不变。本报告不改计算策略，不代表HTTP、并发或完整官方样本成绩。

## 结论与优化优先级

**主要成本是CPU端的数值修复、扫描和完整注意力，合计约77.91%。** 固定中长度路径为满足原数值门槛保留原CPU扫描/注意力，并对NPU投影/MLP结果做CPU临界选点修复。这里定位的是当前软件路径的成本，不是硬件能力上限。

优先研究精度修复中的选点重算：当前归一化估算5.680秒。保持同一选点集合、原2.5e-7保护带和每个输出的K归约顺序，先检查独立输出间是否能复用加载/转换及改善指令流水；不减少修复点、不跳算、不降低门槛。若该部分减少25%，整请求条件估算可省1.420秒；能否做到尚未验证。读取与筛选融合是同组的另一候选，须先测数据流，不能把两者上限相加当已获收益。

第二优先是CPU完整注意力（约4.998秒）与扫描矩阵乘法（约4.635秒），先看保持原数值语义的数据布局/复用方案。已验证变慢的整段扫描单线程不再重复；原生扫描更改答案的方案继续拒绝。

SDK覆盖区间仅约1.761秒，即便理想消除也不足以将31秒降到15秒。三大CPU成本即便都减少一半，条件估算整请求仍约18.90秒。下一轮先证明约1秒级整请求潜力再进入整模型配对；新候选仍须完整34例、保护1e-6及完整18题原门槛，不能用账本代替验收。

## 并行和SDK视图

- 每次SDK调用数：[372, 372, 372]；状态均0。跨线程同步调用时长之和均值3.1892秒，墙钟区间并集1.7920秒，两者不能相加。
- SDK计时是公开rknn_matmul_run入口到返回，包含提交、驱动与等待，**不是NPU纯设备计算时间**。主账本只计它与原生调用/worker等待叶区间的交集；并行worker的CPU工作可能同时发生，这不是逐任务关键路径归因，也不能保证消除SDK耗时就等量节省。
- 插桩请求进程CPU时间均值71.3860 CPU秒；SDK调用线程CPU时间之和均值0.3199 CPU秒。CPU秒跨线程累计，不能与墙钟秒相加，也不能直接当作可省时间。
- CPU扫描覆盖全部6次实际调用，矩阵乘法、三角求解和显式复制/转换另列；不把首次扫描结果外推全模型。频率/温度在请求前后记录，没有持续硬件性能计数，不能据此断言内存带宽已满或到达硬件极限。

## 后续诊断：为何8/16路变慢

r089/r090固定二进制的1040个PMU窗口及2×2对照表明，权重行步幅会放大L1缓存回填；16路另有尾部重复计算，K热循环没有落栈。未采用新布局，未证明整请求省1秒。见[诊断图表](SELECTED_DOT_DIAGNOSIS.html)与[数值、方法边界](SELECTED_DOT_DIAGNOSIS.md)。
