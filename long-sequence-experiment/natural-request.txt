Build a Python service that reconciles inventory updates from several small warehouses. Each warehouse sends JSON events containing an event identifier, a warehouse identifier, a product code, a timestamp, a sequence number, and a signed quantity change. Events can arrive late, out of order, or more than once. The service must produce a consistent current stock view while retaining an audit trail of accepted and rejected events. The initial deployment runs on a single Linux machine with PostgreSQL and should remain understandable to a small engineering team.

Start by defining the event schema and the invariants. Stock belongs to a specific warehouse and product, so updates for one warehouse must never change another warehouse's totals. An exact duplicate must not apply twice. If the same event identifier appears with a different payload, preserve evidence of the conflict and reject the second version. Explain which timestamp is for business reporting and which sequence number determines ordering. Specify what happens when a correction refers to an event that has not arrived yet. Do not silently convert missing identifiers or invalid quantities to empty strings or zero.

Implement a transaction that records the event and updates the materialized stock balance atomically. Discuss the unique constraints and row locks needed when two workers receive updates for the same product at the same time. A process can crash after PostgreSQL commits but before the HTTP response is delivered. Show how a retry recovers the result without repeating the quantity change. Distinguish this from a failure before the transaction commits. Avoid holding database transactions open while waiting for network calls to an external warehouse API.

Expose endpoints for submitting an event, reading a stock balance, and inspecting rejected events. Return explicit error codes for malformed data, payload conflicts, and temporary database failures. A caller should be able to safely retry a temporary failure. Add pagination for the audit log with a stable cursor so concurrent inserts do not cause records to disappear or repeat unpredictably. Warehouse credentials must scope every query to the authorized warehouse. Include an example that proves an identifier in a request body cannot override that authorization boundary.

Provide a migration plan for a table that already contains duplicate event identifiers. First identify conflicting payloads and preserve them for review. Explain how to establish the uniqueness constraint without discarding unexplained records. Describe how a dry run reports its proposed changes, how an operator can stop before a destructive step, and how a repeated migration recognizes work already completed. Include a rollback approach for application code and make clear which historical data changes cannot simply be undone by deploying an older binary.

Finally, write a small focused test suite covering duplicate delivery, conflicting payloads, concurrent updates, commit followed by a lost response, a correction arriving before its target, and access to another warehouse's stock. Show representative JSON requests and responses, SQL schema definitions, and the core Python transaction implementation. Explain the time complexity of the critical operations and suggest useful operational metrics for rejected events, transaction latency, retry rates, and reconciliation lag. Prefer a direct design that can be maintained by the team; justify any queue, cache, retry loop, or background worker with a concrete failure mode it solves.
