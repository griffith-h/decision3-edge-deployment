## 已观察到的机制

32 问题请求的第一批为 8 条序列：最长 765 token，有效 2,797 token，原批次共计算 6,120 个含 padding 的位置。这超过投影/MLP 的 2,048 行加速范围；120 秒诊断仍只跑到该批第 8 层附近，线性计算是主要耗时。另一个 7,232-token 单问题也出现全长 CPU 线性计算，属于下一项待处理问题。

首个候选 `batch_candidate.py` 仅处理 **多序列、各自长度不超过 2,048、原 padded 行数超过 2,048** 的文本批次：按长度拆成单序列调用原模型，再把 logits 恢复到原行顺序。默认 API 批量与容量不变，保留所有序列、选项数和输出位置；其余形状直接调用原路径。

`r010` 把已验证的末位置消费者扩展到长B1：前11层算全部位置，第12层仍生成全部K/V，只计算原D3.logits实际读取的最后query、逐行MLP与norm。保留原12层，公开encoder在调用后恢复；结构、权重版本、方法、hook和模式变化旁路，失败整次重算。长输入65.23s，差0.004144。

`r011` 只对T>4096的softmax独立行使用每worker两CPU线程，两个SDK worker共受四核限制；行内运算次序不变。长输入59.16s，完整输出相对r010数值差0；35项相关边界/数值/故障检查及8请求+34回归+20配对通过。此处仍只是一次长请求实测，不能据此给P95或可靠性承诺。

组合顺序固定为 MLP 在内、拆批在外，避免按拆批前的原尺寸错误改写短路径；投影 scope 在 MLP scope 内部，每次运行另留只读源码快照。长私有消费者在MLP包装之外安装，确保守卫先于MLP临时替换检查；扫描和注意力注册表按反序恢复。下一步按主计划做重复与覆盖验证，原0.01门槛不变。

## 数据、源码与隔离

- `freeze_cases.py` 从原冻结样本取出已暴露的 7 条请求，并加入 115/615-token 自建保护用例，共 9 条。原始载荷只写入忽略的 `output/decision-index-audit/iterations/r001/inputs.json`；6 条已有完整输出另存本地参照。
- `freeze_regression.py` 冻结现有 34 例自建输入；输出参照仅留在本机。发给 RK 的文件只包含推理载荷，不含期望标签或参照答案。
- `host_run.py` 每次创建独立只读源码快照，历史模型/库/图只读，结果目录单独可写。固定镜像、CPU4–7、8GiB、Torch3 / OMP limit4，只运行一个 `decision3-official-opt` 容器。
- `execute.py` 暂停原服务，控制每条诊断 120 秒预算，收集文件后恢复同一原容器并等待健康。预算检测与容器清理存在少量开销；被终止的调用标为开发预算内未完成，不声称正式 600 秒超时或完整计时。
- `probe.py` 不安装 module forward hooks；模块计时包装排除 615-token readout 守卫对象。314-token 请求的 profile 包装已实测与旧输出逐项相同，仍须把 profile 与无包装速度分开。
